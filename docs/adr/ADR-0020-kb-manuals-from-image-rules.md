# ADR-0020: 이미지 기반 규칙의 텍스트 매뉴얼화 및 RAG 연동

## Meta

- **Date**: 2025-12-09
- **Status**: Draft
- **Authors**: PM AI, Claude Code
- **Related**: ADR-0005, ADR-0007, ADR-0014, ADR-0015, ADR-0018

---

## Context (문제 배경)

- 현재 KB/RAG 시스템은 **텍스트 기반 수집 + 임베딩**을 전제로 설계되어 있다.
  - `kb/backfill.py` / `kb/search.py` / `kb/update_embeddings.py`는 카페 게시글의 제목·본문(norm_text)과 내부 텍스트 매뉴얼만을 대상으로 동작한다.
- 그러나 실제 비즈니스 규칙(예: **사알못 비지니스반 포인트 규칙, 무료특강 이후 다시보기 제공 방식, 정규 강의 전환 조건**)은 다음과 같이 **이미지에만 존재**하는 경우가 많다.
  - 강의 공지 이미지(포인트/혜택 안내, 다시보기 조건, 결제/환불 규칙 등)
  - 수강 가이드 인포그래픽
- 이 때문에 다음과 같은 현상이 반복적으로 발생했다.
  1. 사용자는 “사알못 비지니스반은 30포인트가 더 붙는건가?”, “사알못 다시보기 링크?”, “어제 무료강의 신청하려면?”과 같이 **규칙/정책성 질문**을 한다.
  2. RAG는 관련 게시글(예: 메뉴 23 무료특강 글, 메뉴 42 정규 강의 글)은 잘 찾아오지만,  
     이미지 안에만 있는 규칙은 읽지 못한다.
  3. 그 결과:
     - 실제로는 규칙이 존재하지만, RAG 입장에서는 **“자료가 없다 → 정보 없음”**으로 응답하거나,
     - 과거에는 임시 방편으로 붙어 있던 fallback/링크 삽입 로직 때문에 **엉뚱한 링크를 함께 내보내는 문제**가 발생했다.
- AGENTS.md / CLAUDE.md의 핵심 원칙:
  - **폴백(fallback) 금지** – “일단 대충 맞춰서 동작하게” 만드는 우회 로직은 금지.
  - **하드코딩 키워드/룰로 땜질 금지** – 특정 질문 문자열을 직접 if/regex로 걸러서 해결하는 식의 일회성 대응 금지.
  - **SSOT(Single Source of Truth)** – 규칙/정책/설정은 추적 가능한 단일 출처에 기록되어야 한다.
- 동시에, 완전 자동화(OCR 파이프라인 구축)까지는 **복잡도·리스크 대비 효용이 낮다**는 현실적인 제약도 있다.
  - 이미지 레이아웃·폰트·장식 요소에 따라 OCR 품질 편차가 크고,
  - 잘못 추출된 텍스트를 곧바로 RAG에 태우면 오히려 잘못된 규칙을 학습시키는 위험이 있다.

요약하면,

> “중요한 비즈니스 규칙이 이미지에만 있는 상태를 더 이상 방치할 수 없지만,  
>  이를 완전 자동 OCR로 해결하기보다는 **사람이 검증한 텍스트 매뉴얼을 RAG의 SSOT로 두는 구조**가 필요하다.”

---

## Options Considered (검토한 대안)

### Option A: 이미지 OCR 파이프라인 도입

- 개요
  - 강의 공지/매뉴얼 이미지를 자동으로 수집 → OCR → 텍스트로 변환 → 자동 임베딩.
- 장점
  - 운영자가 별도 작업을 하지 않아도 이미지 내용이 자동으로 KB에 반영된다.
  - “이미지 안에만 있는 정보”를 장기적으로는 포괄할 수 있다.
- 단점
  - OCR 품질 편차로 인해 **잘못된 규칙이 KB에 들어갈 위험**이 크다.
  - 이미지 포맷·레이아웃이 자주 바뀌는 환경에서 유지보수 비용이 높다.
  - 현재 프로젝트 범위에서 요구되는 복잡도를 크게 초과한다. (과도한 오버엔지니어링)

### Option B: 웹 UI에 “규칙 편집기” 기능 추가

- 개요
  - Next.js 대시보드에 “규칙/매뉴얼 관리” 화면을 만들고,
  - 운영자가 직접 텍스트를 입력/수정하면, 이를 DB나 별도 스토리지에 저장 → RAG가 이를 우선적으로 사용.
- 장점
  - UI 기반 자기 완결적 운영이 가능하다.
  - 권한 관리, 변경 이력, 버전 관리 등을 UI에서 제공할 수 있다.
- 단점
  - 새로운 페이지·API·인증/권한 모델이 필요하며 구현 범위가 크다.
  - 현재는 AI/스크립트 기반 운영이 중심이라, UI 추가가 **지금 당장의 병목**은 아니다.
  - 동일한 내용을 이미 `docs/` / `kb/manual` 임베딩으로도 관리할 수 있어, 중복 구조 위험이 있다.

### Option C: 텍스트 매뉴얼 계층 도입 (선택)

- 개요
  - 이미지·채팅 등 텍스트가 아닌 출처에만 존재하는 “규칙/정책”을 **사람이 검증해 텍스트로 정리한 매뉴얼**에 모은다.
  - 이 매뉴얼을 KB/RAG 파이프라인의 **SSOT 레이어**로 삼는다.
  - 사용자는 규칙 변경 시 AI(PM/코드)에 자연어로 설명만 하면 되고,  
    AI가 매뉴얼 문서·임베딩·테스트를 갱신하는 방식으로 운영한다.
- 장점
  - OCR 없이도 **정확한 규칙을 안정적으로 RAG에 넣을 수 있다.**
  - 텍스트 매뉴얼은 Git으로 버전 관리되고, 변경 이력이 투명하다.
  - 이미 존재하는 `kb/manual` 임베딩 경로를 그대로 활용할 수 있어, 구조 변경이 최소화된다.
- 단점
  - 운영자가 규칙 변경 시 **한 번은 말을 해줘야 하는 수동 단계**가 있다.
  - 매뉴얼 갱신/임베딩/테스트를 잊으면 규칙이 반영되지 않는다. (운영 프로세스로 보완 필요)

---

## Decision (결정)

**Option C: 텍스트 매뉴얼 계층 도입을 채택한다.**

### 1) 이미지 기반 규칙의 텍스트 매뉴얼화

1. 이미지(강의 공지, 포인트 안내, 다시보기 안내 등)에만 존재하는 중요한 규칙은  
   **반드시 텍스트 매뉴얼 문서로 옮겨 적어야만 “KB에 존재하는 규칙”으로 간주**한다.
2. 위치/구조:
   - 1차 SSOT: `docs/cafe_manuals/*.md`
     - 예: `docs/cafe_manuals/lecture_points_and_passes.md`
   - 2차(실제 RAG 입력): `kb/manual` 임베딩 대상
3. 매뉴얼에는 다음과 같은 내용이 포함된다.
   - 규칙 요약 (예: “사알못 비지니스반은 기본 사알못반보다 30포인트가 추가로 필요하다.”)
   - 예시 질문/대답 (예: “사알못 비지니스반 포인트는 얼마인가요?” → 기대 답변 구조)
   - 관련 카페 메뉴/게시글 번호 (가능한 경우)

### 2) 운영 플로우: “사용자 설명 → AI 매뉴얼화 → 임베딩/테스트”

1. 사용자는 규칙 변경/추가 시, AI에게 자연어로 규칙을 설명한다.
   - 예:  
     > “사알못 비지니스반 포인트 규칙 정리해줘.  
     >  - 비지니스반은 기본 사알못반보다 30포인트 추가  
     >  - 포인트는 ~~ 메뉴에서만 차감 가능 …”
2. PM AI/도우미 AI는 다음 작업을 수행한다.
   - `docs/cafe_manuals/` 아래에 해당 규칙을 설명하는 md 문서를 생성/갱신.
   - 필요 시 `kb/manual` 경로로 복제/정규화하여 임베딩 소스로 사용.
   - `kb/update_embeddings.py`를 통해 manual 타입 임베딩을 재생성.
   - `scripts/verify_rag.py`, `scripts/probe_rag_questions.py` 등에  
     해당 규칙을 검증하는 테스트 케이스를 추가/갱신.
   - 변경 사항을 `docs/CHANGELOG.md` 및 관련 세션 로그, ADR 링크에 기록.

### 3) RAG 파이프라인에서의 활용 원칙

1. `kb/service.py`의 `/ask_llm`에서는:
   - manual 임베딩 결과를 **규칙/정책성 질문에 대해 최우선 근거**로 사용한다.
   - 사알못 비지니스반 포인트, 다시보기 조건, 정규 강의 전환 규칙 등은  
     게시글보다 매뉴얼 내용을 우선 신뢰한다.
2. ADR-0018에서 정의한 out-of-domain 일반 상식 응답 경로는 그대로 유지하되,
   - 매뉴얼/게시글 어디에도 관련 규칙이 없을 때만 `_build_general_answer`를 사용한다.
   - 규칙성 질문(포인트/가격/조건 등)에 대해 **추측으로 일반 상식으로 메운 답변은 금지**한다.

## Invariants (불변식)

1. **이미지에만 있는 규칙은 “매뉴얼로 옮겨 적기 전까지는 KB에 존재하지 않는 것으로 간주”한다.**
   - RAG/LLM이 해당 규칙을 알고 있는지에 대한 기대를  
     이미지 존재 여부가 아니라 매뉴얼/텍스트 존재 여부로 판단한다.
2. **포인트/비지니스반/다시보기/정규 전환과 같은 정책성 답변은 반드시 텍스트 근거를 가져야 한다.**
   - 근거는 카페 게시글 또는 매뉴얼 문서 중 하나여야 하며,
   - 어디에도 근거가 없으면 “정보 없음” 또는 ADR-0018에서 정의한 일반 상식 경로로만 답한다.
3. **fallback/하드코딩 금지 원칙 유지**
   - 특정 질문 문자열(예: “사알못 비지니스반 30포인트”)을 if/regex로 직접 처리하는 임시 방편은 금지.
   - 규칙 변화는 항상 매뉴얼/임베딩/테스트를 통해 반영한다.

---

## Consequences (결과)

### 긍정적 효과

- 이미지에만 있던 중요한 비즈니스 규칙을 **명시적 텍스트 SSOT**로 관리할 수 있다.
- 규칙 변경이 Git/문서/ADR/테스트에 남기 때문에,  
  “왜 이렇게 답하는지”를 나중에 추적할 수 있다.
- RAG가 틀린 규칙을 상상해내거나, 근거 없는 링크를 붙이는 위험이 줄어든다.
- UI를 추가로 만들지 않고도, 사용자가 AI에게 말로 지시하는 방식만으로 **현실적인 운영 루프**를 구성할 수 있다.

### 부정적 효과 / 리스크

- 완전 자동화가 아니므로, 규칙이 변경될 때마다 **매뉴얼 갱신을 잊을 위험**이 있다.
  - 이를 보완하기 위해, 규칙 변경 시 “AI에게 말로 전달 → 매뉴얼/임베딩/테스트 갱신”을  
    운영 체크리스트에 포함시켜야 한다.
- 매뉴얼의 품질(정확성, 최신성)에 따라 RAG 품질이 좌우된다.
  - 잘못된 매뉴얼은 잘못된 규칙을 SSOT로 만들 수 있으므로,  
    변경 시 PM 리뷰/PR 리뷰를 요구한다.

## AI Context (AI 협업 관점 메모)

- 사용자는 “이미지에 있는 내용을 텍스트로 옮겨서 RAG에 넣고 싶다”는 요구를 했고,  
  UI나 OCR보다 **AI에게 구두로 설명 → 매뉴얼/임베딩/테스트를 대신 작성해주는 역할**을 선호한다.
- 향후 AI 세션에서 다음 사항을 기억해야 한다.
  1. 포인트/비지니스반/다시보기 등 규칙성 질문에 대해 “정보 없음”이 반복되면,  
     먼저 해당 규칙이 매뉴얼에 있는지 여부를 확인·제안해야 한다.
  2. 사용자가 규칙을 설명하면, 곧바로 `docs/cafe_manuals/*.md`에 반영하고  
     임베딩/테스트/CHANGELOG까지 한 번에 처리하는 것을 기본 플로우로 삼는다.
  3. “하드코딩/폴백”이 아닌 “매뉴얼+임베딩+테스트” 접근을 기본 선택지로 제안한다.
