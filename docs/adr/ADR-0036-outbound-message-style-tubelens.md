# ADR-0036: 발신 메시지 템플릿(튜브렌즈 스타일) 표준화

## Meta

- **Date**: 2025-12-17
- **Status**: Accepted
- **Authors**: 사용자, GPT-5.2
- **Related Session**: docs/sessions/main.md

## Context (배경)

- `!요약`/Q&A를 포함해, 봇이 발신하는 메시지가 “분석 보고서”처럼 보여 사용자 경험이 나빠졌다.
- 특히 다음 문제가 반복적으로 발생했다:
  - `근거(Evidence)`, `다음 액션(Next Action)` 같은 섹션이 노출됨
  - 로그 타임스탬프/원문 인용(`[2025-…]`)이 노출됨
  - 발신자 이름이 닉네임이 아니라 **userId(숫자)**로 노출됨
  - 모바일에서 줄글이 길어 가독성이 떨어짐
- 운영 목표는 “결론 중심 + 모바일 최적화 + 일관된 톤”이며, 추후 모든 발신 기능에 동일하게 적용돼야 한다.

## Options Considered (고려한 대안)

### Option A: 현 상태 유지(기존 분석 보고서 스타일)
- 장점: 구현 변경 최소
- 단점: 사용자 불만 지속, 운영/신뢰도 저하

### Option B: LLM 프롬프트만 수정(코드 후처리/가드 없음)
- 장점: 적용이 빠름
- 단점: 모델이 가끔 형식을 깨고 userId/타임스탬프를 섞는 문제를 완전히 막지 못함

### Option C: “튜브렌즈 스타일” 표준 문서화 + 프롬프트/후처리/입력 정규화까지 포함 (선택)
- 장점: 일관성 확보, 예외 케이스에서도 규칙을 강제 가능
- 단점: 구현/문서 변경 범위가 커짐(하지만 UX 개선 가치가 더 큼)

## Decision (결정)

**우리는 Option C(튜브렌즈 스타일 표준화)를 선택했다.**

그 이유는:
1. “보고서형 답변”을 구조적으로 방지하려면 프롬프트 + 후처리 + 입력 정규화가 함께 필요하다.
2. 운영 환경에서 userId/타임스탬프 노출은 UX와 프라이버시 측면에서 치명적이므로 강제 차단이 필요하다.
3. 동일한 스타일을 문서/지침으로 고정해 “새 기능 발신”에도 재사용 가능해야 한다.

### Invariants (불변식)
- 사용자에게 **근거/다음 액션/참고 로그** 같은 보고서형 섹션을 출력하지 않는다.
- 사용자에게 **타임스탬프/로그 원문 인용**을 출력하지 않는다.
- 사용자에게 캡처/첨부 **메타 텍스트**(예: `[2025-..png 352x476]`)를 출력하지 않는다.
- 사용자에게 **userId(숫자)**를 출력하지 않는다. 닉네임이 없으면 “어떤 분”처럼 완곡하게 표현한다.
- 답변은 **두괄식 결론 + 공감**으로 시작한다. (“찾아봤어요!” 같은 서두만 단독 금지)
- 답변 본문은 **번호/불릿 구조**, **모바일 줄바꿈**을 기본으로 한다.
- 링크는 본문에 섞지 않고, **푸터(구분선 `---` 아래)**로 분리한다. 단, **링크가 없으면 푸터 자체를 출력하지 않는다**(“없음” 금지).
- 기능이 장애/오류 상태면, 사용자에게는 **고정 문구 3줄**로만 응답한다(원인/디버깅 금지).
- 장애/오류는 **테스트용 오픈채팅방(18462226881291012)**으로만 운영 알림을 보낸다.
  - 운영 알림에는 **roomId/userId를 넣지 않는다**(방 이름 + 기능 + 사유만).
  - “500/internal_error/req_id” 같은 디버깅 용어는 쓰지 않는다.

## Consequences (결과)

### 긍정적 효과
- 모바일 가독성/일관성 개선
- userId/타임스탬프 노출 방지로 프라이버시/신뢰도 강화
- 신규 발신 기능에서도 동일 템플릿을 재사용 가능

### 부정적 효과 / 리스크
- “근거/로그 인용”을 숨기므로, 일부 사용자는 더 자세한 맥락을 원할 수 있다(요청 시에만 별도 UX 설계로 제공).
- 이모지 사용은 방 분위기에 따라 호불호가 있을 수 있어 과도한 사용을 제한해야 한다.
