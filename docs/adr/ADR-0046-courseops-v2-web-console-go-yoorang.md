# ADR-0046: 강의 운영 v2 — 외부 동시접속 CourseOps 웹 콘솔(go.yoorang.kr)

## Meta

- **Date**: 2025-12-23
- **Status**: Accepted
- **Authors**: 운영(PM), Codex CLI
- **Related**: ADR-0039(강의 운영 v2 membership-audit), ADR-0044(`/course` 탭 통합)

---

## Context (배경)

강의 운영 v2(ADR-0039)는 “RAW→VIEW + ACTIONS” 결과를 **구글 스프레드시트**로 산출한다.
하지만 현업 운영 관점에서 다음 문제가 반복되었다.

1. **ACTIONS만 잘 보이면 되는데, 시트는 UI/UX 한계가 크다.**
   - 가독성/정렬/필터/상태 표현(처리 완료/확인 대기/재검증 등)을 시트로 강제하면 유지비가 커진다.
2. **동시접속(여러 운영진)이 필요하다.**
   - 지금까지는 `localhost` 중심이었으나, 운영진이 같은 화면을 동시에 보고 조치/확인해야 한다.
3. **카카오/Redroid 연동 때문에 “수집 주체”는 단 1대여야 한다.**
   - 외부에서 별도 프로그램이 카카오에 로그인/연동하면 세션 충돌(동시 로그인)로 운영이 깨질 수 있다.
4. “조치 완료”는 사람이 눌렀다고 끝이 아니라, **실제 데이터 반영이 되었는지 재검증**이 필요하다.
   - 예: 프리미엄방 미참여 조치 후, 해당 인원이 프리미엄방에 들어왔는지 **빠르게** 확인해야 한다.

따라서 **수집/판정은 12.kakao(에이전트) 1대가 수행**하고,
외부 운영진은 결과를 **웹 UI로 동시접속**하여 보고/조치/검증할 수 있는 구조가 필요하다.

---

## Options Considered (고려한 대안)

### Option A: 스프레드시트(ACTIONS) 계속 사용

- 설명: ACTIONS/OVERVIEW를 계속 시트로 산출하고 운영자가 시트에서 관리
- 장점: 구현 추가가 거의 없음, 누구나 접근 가능
- 단점:
  - “처리 완료/확인 대기/재검증/담당자/시간/메모” 같은 상태를 시트로 안정적으로 운영하기 어렵다.
  - UX 품질을 높이려면 서식/정렬/잔재 제거를 계속 관리해야 한다(유지비 누적).

### Option B: 별도 서비스/별도 레포로 CourseOps를 새로 구축

- 설명: 12.kakao와 분리된 새 서비스가 데이터를 수집/판정/표시까지 모두 담당
- 장점: 도메인/배포를 깔끔하게 분리할 수 있음
- 단점:
  - 카카오/Redroid 연동 주체가 2개가 되어 “동시 로그인/세션 충돌” 위험이 높다.
  - 운영 파이프라인(Watchdog/락/상태 파일)도 이중화되어 장애 면적이 커진다.

### Option C: 12.kakao 내부(기존 web)로 “외부 운영용 콘솔”을 추가 (선택)

- 설명:
  - 수집/판정은 기존 `course-membership-audit-worker`가 수행(12.kakao 1대 고정).
  - 외부 운영진은 `go.yoorang.kr`로 접속해 “ACTIONS(작업 대기열)” 중심 UI를 사용한다.
  - 웹은 카카오에 직접 붙지 않고, 워커가 만든 결과/상태만 조회한다.
- 장점:
  - 카카오/Redroid 연동을 1대로 고정(동시 로그인 문제 회피).
  - UI/UX를 완전히 통제(카드형 작업 대기열, 필터, 처리/검증 상태, 담당자/시간/메모).
  - “빠른 재검증”처럼 운영에 필요한 최적화 로직을 제품에 내장 가능.
- 단점:
  - 외부 접근을 위해 인증/보안/배포(터널/HTTPS) 설계가 필요.
  - 동시접속 환경에서 상태 저장(처리 완료/메모/검증 결과) 영속화가 필요.

---

## Decision (결정)

**우리는 Option C를 선택한다.**

즉,

- 12.kakao(에이전트)는 기존대로 **수집/판정**을 수행한다.
- 외부 운영진용 UI는 `go.yoorang.kr`에서 **ACTIONS 중심의 CourseOps 웹 콘솔**로 제공한다.
- “처리 완료”는 즉시 확정이 아니라, 동기화 후 결과로 **검증(verified/unresolved/unknown)**하여 확정한다.

### Invariants (불변식)

1. **카카오/Redroid 연동 주체는 12.kakao 1대만** 유지한다. (외부 웹은 카카오에 직접 붙지 않는다)
2. `go.yoorang.kr`에는 **CourseOps v2 화면만 노출**한다. (기존 운영 UI(`/settings` 등) 외부 노출 금지)
   - 호스팅: Vercel (`courseops/console/` → `go.yoorang.kr`)
   - 상태/잡/메모 저장소: Supabase Postgres (외부 동시접속을 위한 공유 저장소)
   - DB 비밀번호/토큰/키 같은 시크릿은 **레포/문서/커밋에 저장하지 않는다**. (로컬 `data/`에만 보관)
3. 인증은 **이름 + 공용 비밀번호**로 시작하고, 세션 쿠키로 자동 로그인한다.
   - 접속은 네트워크(IP) 제한을 전제로 하지 않는다(어디서든 접속 가능). 제한은 **인증**으로만 건다.
   - 공용 비번은 교체(로테이션) 가능해야 하며, 로그인 실패 레이트리밋/지연 등 브루트포스 억제 장치가 필요하다.
   - 동기화(재검증/전체 동기화)는 기본 “모두 허용”이지만, 필요 시 **이름 allowlist로 제한** 가능해야 한다.
4. “처리 완료”는 사람이 누른 사실을 기록할 뿐이며, 최종 상태는 동기화 후 결과로 결정한다.
   - 상태: `대기` → `확인 대기` → (`완료(검증됨)` | `미해결(재확인)` | `확인 불가(데이터 미완전)`)
5. 동기화 버튼은 2개로 제공한다.
   - **빠른 재검증**: `확인 대기` 항목이 참조하는 “필요한 방만” 갱신하고 해당 항목만 재판정
   - **전체 동기화**: 톡방+카페+결제SSOT까지 전체 갱신 후 전체 재판정
6. 동기화는 동시 실행을 허용하지 않는다(락/단일 실행).
   - 실행 중에는 “누가/언제 시작했는지”를 표시하고, 중복 요청은 대기/무시한다.
7. 운영 장애는 “수동 복구”가 아니라 **Watchdog 감지 → 자동 조치**가 기본이다.
   - 워커/동기화가 멈추면(heartbeat/progress 갱신 중단) 자동 재기동으로 복구되어야 한다.

---

## Consequences (결과)

### 긍정적 효과

- 운영진이 “해석”이 아니라 “처리”에 집중할 수 있다(ACTIONS 카드형 UI).
- 담당자/시간/메모 + 검증 상태로, 동시접속에서도 충돌/누락을 줄일 수 있다.
- 카카오 세션 충돌을 구조적으로 방지한다(수집 주체 1대 고정).

### 부정적 효과 / 리스크

- 외부 공개(도메인)로 인해 인증/보안/운영(HTTPS/터널/접근제어) 책임이 증가한다.
- “빠른 재검증”이 제대로 동작하려면 ACTION을 안정적으로 식별할 수 있는 key 설계가 필요하다.

### 후속 작업

- [ ] 문서(레퍼런스): `docs/reference/course-ops-v2-web-console.md` 추가
- [ ] SSOT 갱신: `docs/ssot.md`에 전환 결정 기록
- [ ] UI:
  - [ ] `courseops/console/`에 `go.yoorang.kr` 전용 CourseOps 화면 추가(작업 대기열/대시보드/전체 명단/설정)
  - [ ] 로그인(이름+공용 비번) + 자동로그인(쿠키) + 동기화 권한 allowlist
- [ ] API/저장소:
  - [ ] `ACTIONS` 산출 결과를 웹에서 조회 가능한 형태(JSON 스냅샷)로 제공
  - [ ] 처리/메모/검증 상태를 영속 저장(append-only audit 포함)
  - [ ] “빠른 재검증” 입력(확인 대기 항목 기준으로 필요한 방만 갱신)
- [ ] 운영/배포:
  - [ ] `go.yoorang.kr` 도메인 연결(runbook) 문서화(터널/HTTPS)
  - [ ] 동기화/워커 단일 실행 락 + watchdog 자동 복구 연계
