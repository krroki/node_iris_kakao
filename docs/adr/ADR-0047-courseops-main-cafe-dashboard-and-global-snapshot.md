# ADR-0047: CourseOps 메인 카페 홈 지표(글로벌 스냅샷)

## Meta

- **Date**: 2025-12-26
- **Status**: Accepted
- **Authors**: 운영(PM), Codex CLI
- **Related**: ADR-0039(강의 운영 v2 membership-audit), ADR-0046(CourseOps 웹 콘솔)

---

## Context (배경)

강의 운영은 “강의 카페 + 3개(또는 2~4개) 오픈채팅방” 단위로 진행되지만, 운영의 뿌리는 **메인 카페**다.

- 강의 카페는 강의 시작 후 약 3개월이 지나면 활동/점검 빈도가 줄어드는 편이다.
- 반면 메인 카페는 지속적으로 신규/등업/활동/운영 이슈가 발생하므로 **장기적으로 계속 관리**가 필요하다.

따라서 CourseOps 홈(대시보드)에서 **메인 카페의 핵심 지표**를 함께 볼 수 있어야 한다.

제약:

- 외부 웹(예: Vercel)에서 네이버 로그인을 직접 처리하면 계정/쿠키/봇탐지/창 다중 실행 등 운영 리스크가 커진다.
- 카페 멤버 수집은 이미 로컬(12.kakao PC)에서 수행할 수 있는 크롤러/프로필/쿠키 흐름이 존재한다.

---

## Options Considered (고려한 대안)

### Option A: 코스 스냅샷(payload)에 메인 카페를 “붙여서” 저장

- 장점: 구현이 단순하다.
- 단점:
  - 코스마다 동일한 메인 카페 데이터가 중복 저장된다.
  - 코스 동기화 주기와 메인 카페 관리 주기가 섞여, 홈 지표의 의미가 흐려진다.

### Option B: 메인 카페를 “글로벌 스냅샷”으로 분리 저장 (선택)

- 장점:
  - 코스와 독립된 주기/상태로 관리 가능(장기 운영 지표로 적합).
  - 중복 저장을 피하고, UI에서도 “메인 카페” 섹션을 명확히 분리할 수 있다.
- 단점:
  - DB/스토어/API가 1세트 더 필요하다.

### Option C: 웹 콘솔에서 메인 카페를 실시간 크롤링

- 장점: 데이터가 즉시 최신.
- 단점:
  - 로그인/쿠키/보안/봇탐지 대응이 어려워 운영 비용과 장애 가능성이 크다.

---

## Decision (결정)

**우리는 Option B(글로벌 스냅샷)를 선택했다.**

- 로컬 에이전트(12.kakao PC)가 유휴 상태에서 메인 카페 멤버 스냅샷을 주기적으로 수집한다.
- 수집 결과를 Postgres(Supabase)에 `courseops_global_snapshots`로 업서트한다.
- 웹 콘솔(대시보드)은 이 스냅샷을 읽어 “메인 카페” 섹션에 사람이 이해 가능한 지표로 보여준다.

---

## Invariants (불변식)

1. 웹 콘솔은 네이버 로그인/크롤링을 직접 수행하지 않는다. (로컬 에이전트만 수행)
2. 계정/비밀번호 등 민감정보는 UI/로그/DB에 남기지 않는다.
3. 메인 카페 지표는 “운영이 바로 판단/조치할 수 있는 형태”로만 노출한다. (개발자 용어 최소화)
4. 메인 카페 데이터는 코스 동기화와 독립적으로 관리 가능해야 한다.

---

## Consequences (결과)

### 긍정적 효과

- 대시보드에서 메인 카페의 흐름(규모/등급/활동)을 즉시 확인할 수 있다.
- 강의 카페가 조용해져도 메인 카페를 지속적으로 관리하는 운영 습관을 유지할 수 있다.

### 부정적 효과 / 리스크

- 로컬 크롤러 장애/로그인 만료 시 데이터가 갱신되지 않을 수 있다.
  - 이 경우에도 UI는 디버깅 용어 없이 “가져오지 못했어요/다시 시도할게요” 수준으로만 안내한다.

---

## 구현 메모 (현재 노출 지표)

- 총 멤버 수
- 최근 7일 신규 가입 수
- 최근 7일/30일 활동(최근 방문) 수
- 등급 분포(상위 N개)
