# [PRD] 강의 운영 v2 — CourseOps 웹 콘솔(ACTIONS 중심, go.yoorang.kr)

## 1) 배경 / 문제

강의 1개는 보통 아래 데이터가 흩어져 있다.

- 카카오 오픈채팅 3개(사담방/공지방/프리미엄방)의 **현재 참여자**
- 네이버 카페(비공개)의 **가입자/등급**
- 결제 확인용 구글시트(수기 SSOT)의 **결제 트랙(일반/프리미엄) + 기본 정보**

운영진은 “누가 어떤 방에 있어야 하는지 / 닉네임 규칙을 지키는지 / 결제 트랙과 권한이 맞는지”를 빠르게 확인해야 하지만,
데이터가 분산되어 있어 매번 수동 교차검증이 필요했다.

## 2) 목표(Outcome)

운영자가 **웹 콘솔 1개**에서 아래를 바로 처리할 수 있게 한다.

- (입장) 들어와야 하는 방에 없는 사람을 바로 찾아 **입장 안내**
- (닉네임) 닉네임 규칙이 깨진 사람을 찾아 **닉네임 변경 요청**
- (권한) 일반반/프리미엄반 권한이 꼬인 케이스를 찾아 **정리**
- (누락) 결제 SSOT 누락/카페닉 불일치 등을 찾아 **확인 요청**
- (기록) 변동 사항이 무엇이었는지 **이력 확인**
- (검증) 운영진이 조치 후 “실제로 반영됐는지”를 **빠른 재검증**으로 확인해 완료를 확정

## 3) 비목표(Non-goals)

- 자동으로 카카오톡을 발송하지 않는다.
- 결제 SSOT 시트에 쓰기(편집)하지 않는다. (읽기 전용)
- “데이터가 불완전한데도 정상 처리” 같은 임의 판단은 하지 않는다.

## 4) 사용자/운영자(Primary User)

- 강의 운영 담당(비개발자)

## 5) SSOT / 우선순위 규칙

### 5.1) 트랙(일반/프리미엄) SSOT

- 트랙은 **결제 SSOT**를 1순위로 본다.
- 결제 SSOT가 없거나 공유가 안 된 경우에는 “확정 불가”로 남기며, 카페 등급만으로 강제 확정하지 않는다.

### 5.2) 운영진 예외

- 운영진/스탭은 “필수방 미참여” 체크 대상에서 제외한다.
- 단, 닉네임 규칙 위반은 운영진이라도 별도 정책이 있다면 추후 옵션으로 분리한다.

## 6) 닉네임 규칙(기본)

### 6.1) 톡방 닉네임 기본 규칙

- 형식: `이름마스킹(카페닉)`
- 이름마스킹 규칙(권장):
  - 첫 글자 + `@` 반복 + 마지막 글자
  - 예: `정영록` → `정@록`
  - 예: `정영일록` → `정@@록`

### 6.2) 예외/허용(운영 편의)

- 슬래시 케이스(예: `유@비/냥댕`)는 “참여로는 인정”하되, `닉네임 변경 요청` 대상으로 잡는다.
- 띄어쓰기 차이(예: `오남매워킹맘` vs `오남매 워킹맘`)는 “동일인 가능성”을 고려해 매칭을 보완한다.

## 7) 결과물(구글시트 탭 구성)

운영 UI는 `go.yoorang.kr`에서 제공되는 **CourseOps v2 웹 콘솔**을 1순위로 한다.

### 7.1) 화면(웹)

#### 작업 대기열(ACTIONS)

- 운영자가 “그대로 처리”하는 카드형 큐
- 필수 요소:
  - 해야 할 일 / 사유 / 필요한 방 / 현재 닉네임 / (필요 시) 바꿀 닉네임
  - `처리 완료` 버튼(담당자/시간 자동 기록, 메모는 선택)
  - 처리 상태: `대기` → `확인 대기` → `완료(검증됨)`/`미해결(재확인)`/`확인 불가(데이터 미완전)`
- 필터/정렬:
  - 우선순위/유형/방 기준으로 빠르게 좁혀 볼 수 있어야 한다.

#### 대시보드(요약)

- 운영자가 “상태를 한눈에” 보는 카드/차트 요약
- 예: 대기 작업 수, 트랙 분포, 준수율, 유형별 분포

#### 전체 명단(통합 뷰)

- 운영진이 “누가 어디에 있어야 하는지”를 빠르게 스캔하는 표
- 정상/불필요/이상(조치 필요)이 시각적으로 구분되어야 한다.

#### 설정(데이터 소스/규칙)

- 결제 SSOT(읽기) / 카페 / 규칙 토글 / 동기화 권한 제한(allowlist) 등을 설정한다.

### 7.2) 데이터 소스(입력)와 기록(영속)

- 수집/판정은 12.kakao(에이전트) 1대가 수행한다(카카오/Redroid 동시 로그인 방지).
- 결제 SSOT는 Google Sheets(읽기)로 유지한다.
- 처리/검증/메모 기록은 웹에서 영속 저장되어야 한다(동시접속 충돌 방지).

### 7.3) (레거시/선택) 구글시트 산출

스프레드시트는 “운영 UI”가 아니라 **백업/내보내기(export)** 용도로만 유지한다.

- `CAFE_RAW`/`OPENCHAT_RAW`/`SSOT_RAW`/`RULES_RAW`/`AUDIT_VIEW`/`AUDIT_LOG` 등은 필요 시 유지
- `ACTIONS`/`OVERVIEW`는 웹이 안정화되면 더 이상 운영의 1순위가 아니다

## 8) 운영 워크플로우(최소)

1. 코스 설정
   - `clubId`(카페) + 코스 스프레드시트 URL/ID + 결제 SSOT URL/ID 입력
2. 동기화(데이터 최신화)
   - `전체 동기화`: 톡방+카페+결제SSOT까지 최신화
3. 작업 대기열에서 조치
4. 조치 후 `처리 완료` → `확인 대기`
5. `빠른 재검증`으로 실제 반영 확인 후 `완료(검증됨)` 확정

## 9) 품질/안정성 요구사항(중요)

- 외부 운영 UI는 “해석 없이 처리”가 목표다. 문구/표현/상태는 사람 단어로만 표시한다.
- `처리 완료`는 검증 전에는 완료로 확정하지 않는다(반드시 `확인 대기`를 거친다).
- `빠른 재검증`은 `확인 대기` 항목에 필요한 방만 갱신해, 조치 확인을 빠르게 끝낸다.
- 동기화는 단일 실행(락)이어야 하며, 실행 중에는 누가/언제 시작했는지 표시한다.
- 워커 중복 실행으로 크롬/카페 창이 여러 개 뜨는 상황은 **자동으로 1개만 남기도록** 복구되어야 한다(watchdog).

## 10) 성공 기준(Acceptance Criteria)

- 운영자가 “작업 대기열”만 보고 해석 없이 조치할 수 있다.
- 운영자가 조치 후 `빠른 재검증`으로 “진짜 반영됐는지” 확인할 수 있다.
- 담당자/시간이 자동 기록되고, 메모(선택)로 맥락을 남길 수 있다.
- 동시접속 환경에서도 동기화/상태가 꼬이지 않는다(락 + 영속 저장).
