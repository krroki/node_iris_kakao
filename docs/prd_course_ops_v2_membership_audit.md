# [PRD] 강의 운영 v2 — 강의 정리 시트(코스 단위)

## 1) 배경 / 문제

강의 1개는 보통 아래 데이터가 흩어져 있다.

- 카카오 오픈채팅 3개(사담방/공지방/프리미엄방)의 **현재 참여자**
- 네이버 카페(비공개)의 **가입자/등급**
- 결제 확인용 구글시트(수기 SSOT)의 **결제 트랙(일반/프리미엄) + 기본 정보**

운영진은 “누가 어떤 방에 있어야 하는지 / 닉네임 규칙을 지키는지 / 결제 트랙과 권한이 맞는지”를 빠르게 확인해야 하지만,
데이터가 분산되어 있어 매번 수동 교차검증이 필요했다.

## 2) 목표(Outcome)

운영자가 **구글 스프레드시트 1개**에서 아래를 바로 처리할 수 있게 한다.

- (입장) 들어와야 하는 방에 없는 사람을 바로 찾아 **입장 안내**
- (닉네임) 닉네임 규칙이 깨진 사람을 찾아 **닉네임 변경 요청**
- (권한) 일반반/프리미엄반 권한이 꼬인 케이스를 찾아 **정리**
- (누락) 결제 SSOT 누락/카페닉 불일치 등을 찾아 **확인 요청**
- (기록) 변동 사항이 무엇이었는지 **이력 확인**

## 3) 비목표(Non-goals)

- 자동으로 카카오톡을 발송하지 않는다.
- 결제 SSOT 시트에 쓰기(편집)하지 않는다. (읽기 전용)
- “데이터가 불완전한데도 정상 처리” 같은 임의 판단은 하지 않는다.

## 4) 사용자/운영자(Primary User)

- 강의 운영 담당(비개발자)

## 5) SSOT / 우선순위 규칙

### 5.1) 트랙(일반/프리미엄) SSOT

- 트랙은 **결제 SSOT**를 1순위로 본다.
- 결제 SSOT가 없거나 공유가 안 된 경우에는 “확정 불가”로 남기며, 카페 등급만으로 강제 확정하지 않는다.

### 5.2) 운영진 예외

- 운영진/스탭은 “필수방 미참여” 체크 대상에서 제외한다.
- 단, 닉네임 규칙 위반은 운영진이라도 별도 정책이 있다면 추후 옵션으로 분리한다.

## 6) 닉네임 규칙(기본)

### 6.1) 톡방 닉네임 기본 규칙

- 형식: `이름마스킹(카페닉)`
- 이름마스킹 규칙(권장):
  - 첫 글자 + `@` 반복 + 마지막 글자
  - 예: `정영록` → `정@록`
  - 예: `정영일록` → `정@@록`

### 6.2) 예외/허용(운영 편의)

- 슬래시 케이스(예: `유@비/냥댕`)는 “참여로는 인정”하되, `닉네임 변경 요청` 대상으로 잡는다.
- 띄어쓰기 차이(예: `오남매워킹맘` vs `오남매 워킹맘`)는 “동일인 가능성”을 고려해 매칭을 보완한다.

## 7) 결과물(구글시트 탭 구성)

코스당 1개 스프레드시트 문서를 사용한다.

### 7.1) 운영 탭(derived)

#### ACTIONS (할 일 큐)

- 운영자가 “그대로 처리”하는 탭
- 상단 요약: `총/입장 안내/닉네임 변경/결제 확인/카페닉 확인/권한 정리/데이터 점검`
- 본문 컬럼:
  - `우선순위` (지금/오늘/확인/정리)
  - `해야 할 일` (예: 입장 안내, 닉네임 변경 요청)
  - `사유` (왜 이 일이 생겼는지 한 줄)
  - `대상` (카페닉 기준)
  - `필요한 방`
  - `바꿀 닉네임`
  - `현재 닉네임`

#### OVERVIEW (요약)

- 운영자가 “상태를 한눈에” 보는 요약 탭
- 자세한 설계/표현은 ACTIONS가 충분히 단순해지면 OVERVIEW는 최소화한다.

### 7.2) 원천/이력 탭(raw/view/log)

- `CAFE_RAW`: 카페 멤버(등급 포함) upsert
- `OPENCHAT_RAW`: 톡방 멤버 upsert(3방)
- `SSOT_RAW`: 결제 SSOT(읽기) upsert
- `RULES_RAW`: 코스 설정 스냅샷
- `AUDIT_VIEW`: 카페닉 단위 통합 뷰
- `AUDIT_LOG`: 변경 이력(append-only)

## 8) 운영 워크플로우(최소)

1. 코스 설정
   - `clubId`(카페) + 코스 스프레드시트 URL/ID + 결제 SSOT URL/ID 입력
2. 1회 실행(업서트)
3. `ACTIONS`에서 위에서부터 처리
4. 안정화되면 주기 점검으로 유지

## 9) 품질/안정성 요구사항(중요)

- derived 탭(`OVERVIEW`/`ACTIONS`)은 매번 **시트 전체를 먼저 깨끗하게 정리한 뒤** 다시 그린다.
  - 값만 지우는 `values.clear`로는 부족(기존 서식/merge/색상 잔존 가능)
- 워커 중복 실행으로 크롬/카페 창이 여러 개 뜨는 상황은 **자동으로 1개만 남기도록** 복구되어야 한다(watchdog).

## 10) 성공 기준(Acceptance Criteria)

- 운영자가 ACTIONS만 보고 “무슨 행동을 해야 하는지” 해석 없이 처리할 수 있다.
- ACTIONS 상단 요약이 “우선순위 숫자 나열”이 아니라, **업무 종류 건수**로 보인다.
- `바꿀 닉네임`이 가능한 한 구체적으로 제안된다(결제 SSOT의 `성함` 활용).
- derived 탭 아래쪽에 예전 서식(검은 줄/merge)이 남지 않는다.
